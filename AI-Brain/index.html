AI-Brain • Unified Intelligence Layer

✦

Gemini supplies the reasoning engine. AI-Brain supplies expandable knowledge, retrieval logic, project context, memory structures, personas, creator patterns, specialist methods, safety boundaries, and tool-selection intelligence.

AI-Brain is designed as one reusable brain that understands what the user is trying to do, selects the right knowledge, and keeps project reality coherent. The user should be able to describe a goal in ordinary language; AI-Brain can infer the domains, output types, constraints, project state, safety requirements, and tools that matter, then retrieve a focused set of knowledge for the model.

Intent becomes a capability bundle. A book-cover request can become book + art + layout + branding + image. A new TTRPG can become rules + TTRPG + maps + worldbuilding + sheets + strategy + organization + art + safety/accessibility. A social network can become code + authentication + profiles + messaging + moderation + privacy + notifications + media + organization.

Repository rule

The target root is intentionally small: index.html, js/, json/, docs/, and assets/. The intelligence can be enormous inside those areas, but the root should remain predictable and easy for both humans and the backend to navigate.

SECTION 1

Executive Pitch

One reusable brain that understands what the user is trying to do, selects the right knowledge, and keeps project reality coherent.

AI-Brain is a general-purpose intelligence layer built around a simple idea: the model should not need the user to know which specialist modules to request. The user describes the goal in ordinary language. AI-Brain infers the domains, output types, constraints, project state, safety requirements, and tools that matter, then retrieves only the most relevant knowledge and gives Gemini a focused working context.

The repository is therefore not merely a pile of reference files. It is a structured, expandable brain: a capability directory, domain corpus, retrieval map, creator toolkit, project ontology, reasoning aid, and set of reusable specialist patterns that can be shared across books, games, websites, social systems, art tools, health-support projects, virtual pets, TTRPGs, MMORPGs, simulations, and future projects that do not yet exist.

Product promise

  • A user asks for an outcome, not a module name. AI-Brain identifies the needed capability bundle automatically.
  • The same backend can serve multiple unrelated applications without mixing project state, canon, personal records, or private content.
  • Knowledge remains expandable: adding well-described JSON/JS shards can increase domain coverage without rewriting the entire backend.
  • Gemini remains the reasoning engine; the GitHub corpus supplies grounded specialist knowledge and project patterns through retrieval.
  • AI-Brain can remember, organize, create, reason, simulate, code, analyze, track, roleplay, retrieve, and orchestrate tools while preserving source and project boundaries.
  • The system should scale from a single character or worksheet to a book series, game world, social platform, virtual tabletop, healthcare support corpus, or entire fictional galaxy.

The goal is breadth through composition

No one human should have to pre-imagine every future use case. AI-Brain should combine reusable capabilities. A “book cover” request becomes book + art + layout + branding + image. A “new TTRPG” request becomes rules + ttrpg + maps + worldbuilding + sheets + strategy + organization + art + safety/accessibility. A “private social network” request becomes code + authentication + profiles + messaging + moderation + privacy + notifications + media + organization. The combinations are discovered from the request, not hardcoded as one recipe per project.

North-star, not a false guarantee

The design target is frontier-chat-assistant breadth plus a user-maintained, project-aware intelligence corpus. Model/provider limits still exist; “more” comes from better retrieval, structure, tools, memory, specialist knowledge, and project continuity, not from pretending the GitHub files alter Gemini’s model weights.

SECTION 2

What AI-Brain Is — and Is Not

A clean division between model intelligence, reusable corpus knowledge, project data, and user-facing applications.

LayerResponsibility
GeminiReasoning, language, multimodal understanding, generation, tool-choice reasoning, synthesis, and response creation.
AI-Brain GitHub corpusReusable domain knowledge, specialist methods, routing metadata, schemas, creator patterns, validation rules, examples, reusable assets, and retrieval targets.
AI-Brain backendAuthentication, provider routing, tool execution, memory, project records, corpus indexing/search, persistence, assets, bots/personas, code assistance, jobs, auditing, and rate/capability control.
Calling projectProject-specific canon, user-owned content, game state, manuscript state, personal records, project-specific files, permissions, and UI.
UserFinal authority over creative canon, goals, personal choices, sensitive records, and decisions that should not be silently overwritten.

Five design boundaries

1. Retrieval, not model-weight modification. The corpus is source material selected into context; Gemini remains the model.

2. Global knowledge is not personal truth. Generic psychiatry, disability, writing, coding, safety, or game knowledge must never be treated as facts about a specific user or project.

3. Project isolation. One project can share global capabilities without leaking its private facts into another project.

4. No silent canon mutation. When a request conflicts with established project facts, surface the conflict, ask or record intentional retcons, and preserve provenance.

5. Human authority for high-impact decisions. AI may assist with moderation, health education, editing, safety triage, and strategy; it should not quietly become the sole authority where context, consent, or human review matters.

What “the brain” means here

The GitHub AI-Brain is the reusable knowledge and selection layer: it teaches the backend what kinds of intelligence exist, where to find them, how they combine, what they are allowed to do, and what structured outputs are useful. This is what lets a single model request become project-aware rather than generic.

SECTION 3

Core Intelligence Architecture

A layered system that turns an open-ended user request into grounded, project-aware action.

StageAI-Brain responsibility
1. Request understandingParse goal, audience, desired output, constraints, domain clues, urgency, privacy scope, and whether the user wants explanation, creation, editing, planning, simulation, or action.
2. Capability taggingAssign multiple weighted capability tags and negative constraints; preserve ambiguity when multiple interpretations are plausible.
3. Project scopeLoad only the current project’s relevant records, canon, files, tasks, bots, timeline, rules, and permissions.
4. Memory selectionRetrieve durable user/project memories that are relevant to the current goal instead of dumping all memory into context.
5. Corpus retrievalScore GitHub shards by metadata and path, fetch only a small candidate set, rank records inside them, and cap total context.
6. Persona/role selectionApply the requested persona or specialist mode: friend, editor, strategist, NPC, game bot, health-support guide, coder, organizer, creator, etc.
7. Tool routingChoose tools only when needed: project search, memory, calculation, code, image, web, file operations, external tools, 3D jobs, generators, or health-specific retrieval.
8. Model tier routingUse the everyday Gemini tier by default; elevate difficult reasoning to the reasoning tier when justified; fall back when needed.
9. Output validationCheck schema, project rules, safety, provenance, permissions, continuity, and requested format before returning or saving.
10. PersistenceSave only what the request and permissions allow: project records, generated assets, tasks, memory, bot state, code files, exports, or audit metadata.
Massive-corpus rule

AI-Brain should never send the entire GitHub repository to Gemini. The current backend already expresses the scalable pattern: index tree metadata, score shards before download, fetch only a few, rank records inside them, and cap the final model context.

SECTION 4

Intent-to-Capability Selection Engine

The part that makes “I do not know what modules I need” a solvable problem.

The selector should treat each user request as a multi-label problem. A request can activate many domains at once. The router should infer both what the user explicitly asked for and the supporting capabilities implied by the task.

Selection logic

1. Extract explicit nouns and verbs: “create a cover,” “debug login,” “build a campaign,” “sort files,” “help me calm down.”

2. Infer hidden dependencies: a cover needs layout/branding; a social network needs auth/privacy/moderation; a TTRPG needs rules/sheets/maps; a health-support worksheet needs accessibility and safety-aware language.

3. Add project-type context: a “map” in LiteraryFriend may be story art, while a “map” in TableGate may need interactive geometry, fog, pins, and VTT rules.

4. Retrieve high-confidence core domains first, then secondary domains only if they contribute concrete knowledge or tools.

5. Use negative routing to avoid irrelevant material. Example: “book cover” should not retrieve psychiatric material merely because a character has depression.

6. Return an internal routing trace in debug/audit mode: selected tags, why they were selected, candidate shards, and context budget.

Current-tree migration note

The GitHub location currently also exposes backend/ and css/ alongside the desired root entries, while index.html is only a placeholder. The target contract in this pitch removes those extra root categories from AI-Brain and treats the repository as an intelligence corpus rather than a backend or styling package.

Root rules

  • No ZIP archives anywhere in docs/.
  • No backend source code in docs/.
  • No CSS root folder in the final AI-Brain contract; visual knowledge/patterns belong in JSON/JS, while public index styling can remain inside index.html if needed.
  • No backend root folder in the final AI-Brain contract. The Apps Script backend is developed/deployed separately.
  • JSON folders stay shallow and domain-based so the retrieval index can infer meaning from paths.
  • JavaScript files should be reusable intelligence/selectors/helpers, not frontend application bundles.
  • Assets are human-usable HTML materials such as worksheets, printables, handouts, and diary cards.
  • Private project/user data does not belong in the public GitHub corpus.

Design principle: data-driven routing

The router should not grow into a giant chain of “if user says X, load these exact files.” JavaScript should understand capability metadata. JSON shards should describe what they know and what they are useful for. That makes new intelligence discoverable by metadata and path instead of requiring a backend edit every time a new subject is added.

SECTION 17

Safety, Accessibility, Provenance & Human Authority

Intelligence is more useful when the system knows where it can act, where it should assist, and where a human stays in control.

Safety and moderation lessons from TableGate

  • Automated moderation can assist with spam, scam, grooming/threat signals, triage, and evidence organization, but should not be the sole decision-maker for meaningful enforcement.
  • Human review and appeal should remain available; automated detection can miss context and disproportionately flag marginalized users.
  • Blocking/reporting should preserve relevant evidence instead of destroying it.
  • High-impact safety records need audit trails, access controls, source/version preservation, and anti-retaliation thinking.
  • Privacy, age, consent, and safety exceptions should be explicit in product/data schemas rather than implicit in model prompts.

Accessibility as an intelligence domain

  • Keyboard, touch, switch/gamepad, reduced-motion, screen-reader, caption/text-equivalent, low-sensory, no-camera, and flexible communication considerations.
  • Support needs should be treated as concrete requirements, not as a reason to lower quality or exclude a user.
  • AI responses can adapt cognitive load: smaller steps, structured choices, clearer wording, or detailed technical output depending on the user/request.
  • Generated assets and schemas should not rely on color alone and should preserve meaningful text alternatives where applicable.

SECTION 18

Growth Model: How the Brain Expands

Adding new intelligence should feel like teaching the library, not rebuilding the entire AI.

1. Create or obtain a new knowledge source.

2. Normalize it into one or more shallow domain shards with schema/version/domain/capabilities/intents/provenance metadata.

3. Add any selector/helper logic to js/ only when the knowledge introduces genuinely new routing behavior or reusable validation — not for every new file.

4. Update allowed manifests/audits in docs/ and validate the repository contract.

5. Refresh/index the corpus so the backend sees new paths and metadata.

6. Run routing tests with representative user prompts and verify that the new shard is retrieved only when useful.

7. Run conflict/duplication checks against existing corpus knowledge.

8. Add public-project metadata to index.html only if the project itself is meant to be public.

9. Keep private project/user facts in the project’s own storage; never “teach” the public corpus by uploading sensitive personal state.

Scalability principle

Corpus size can grow dramatically because retrieval is targeted. The backend’s intended large-corpus design indexes file metadata, scores candidate shards before download, retrieves a small number of relevant shards, ranks records within them, and caps the final context. A large health, writing, game, or programming library therefore improves available grounding without forcing every request to carry the entire repository.

What requires a backend change vs. what should not

ChangeBackend edit?
Add new JSON knowledge on an existing domainUsually no; index/metadata should make it discoverable.
Add new reusable routing synonym/tagUsually JS corpus helper/registry update; backend should remain stable.
Add new projectNo for corpus use; add public index entry only if public.
Add new provider/tool/actionYes, backend/provider/tool adapter work may be required.
Add new structured record typePrefer generic records/schemas first; backend edit only if new specialized behavior is needed.
Add personal project dataNo GitHub change; store in the calling project.
